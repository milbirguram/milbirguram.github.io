# Whittle

Six small functions, each with a planted bug, each with three or four ordinary example tests that pass anyway. The visitor states a property, a small property-based tester throws random inputs at the function until one fails, and a shrinker whittles the failure down to an input from which no single simplification still fails. The card preview replays real engine runs on five of the functions (fixed seeds listed in `model.js` and checked by the tests) and loops through a stream of inputs, one failure, and its shrink. Page: `projects/whittle/index.html`. Engine and functions: `model.js` (browser and Node). Page logic: `app.js`. Tests: `tests/model.test.js`.

## What it’s for

A test’s job is to try to refute the code, not to confirm it. Example tests written by the person who wrote the function tend to test the cases that person already had in mind, so they pass. A property stated for every input, checked against many generated inputs, goes looking for the cases nobody had in mind, and one counterexample outweighs any number of passing examples. The page also shows the two ways this goes wrong in practice: a property too weak to fail, and a precondition that throws away the inputs that matter. Shrinking matters because a small counterexample is the most useful thing a test can give you: it points at the cause.

## How I know

**What is modelled.** `model.js` is a real, small property-based testing engine, written for this page:

- *Generation.* A seeded PRNG (mulberry32) drives generators for integers, lists, strings, records and calendar dates (ISO strings, UTC, counted in days from 2024-01-01), plus `map`. Each run has a size that grows by one per input (1 + i, capped at 30), close to QuickCheck’s own schedule, and size only caps ranges and average lengths. An earlier version grew size three times more slowly; the first failure was then usually already tiny, so a quarter of `dedupe` runs and a third of run-length runs shrank in one step or none, which hid the whittling the page is about. Integers that span zero draw a magnitude and then a sign, and the sign is drawn even for 0, so lowering a magnitude to 0 never shifts the choices after it. Lists draw a yes/no choice before each further element, so their length is geometric with a mean set by size. Strings for the run-length example first pick how many letters of the alphabet they may use (one to four), so long single-letter runs are common rather than astronomically rare. That generator choice is what lets the tester find a run of ten in about 17 inputs on average.
- *Choice sequences.* Following Hypothesis (MacIver et al. 2019; MacIver and Donaldson 2020), every input is built from a recorded sequence of integer choices, and shrinking edits that sequence, never the value. A candidate is replayed through the same generator: out-of-range choices are clamped and missing ones read as 0. So every shrunk input is one the generator could have produced. This is why a separate shrinker per type is not needed.
- *Shrinking.* Three passes are repeated until a whole sweep changes nothing: delete a block of 8, 4, 3, 2 or 1 consecutive choices; set such a block to zero; lower one choice (to 0, then by binary search, which tries half the value first and ends having tried one less). A candidate is accepted only if it still fails the property and its choice sequence is strictly smaller in shortlex order (shorter first, then lexicographically). Shortlex is a well-order on these sequences, so shrinking always terminates. There is a budget of 60,000 property calls, which no tested shrink came near.
- *Reporting.* A run records every input it tried and its outcome (pass, fail, or skipped by a precondition), the seed, the failing input with its choices and size, and every accepted shrink step with the pass that made it. The page shows exactly these. The scoreboard text is built by `scoreboard()` in the model from those records.

**The functions.** Each is ordinary JavaScript with one realistic bug, and a fixed version. The page shows the functions’ own source text (`Function.prototype.toString`), so the code on screen is the code that runs. The line marked after a failure is found by a marker string that the tests check occurs exactly once in the buggy source and not at all in the fixed one. That line is chosen by hand: the engine finds that the code is wrong, not where.

| Function | Bug | Strong property | Weak properties (pass despite the bug) |
|---|---|---|---|
| `dedupe` | keeps the *last* copy (`lastIndexOf`), so order changes | matches a plain first-copy loop | no repeats in output; every input value is kept |
| `encode` / `decode` | decode reads one digit of the count, so runs over nine break | `decode(encode(s)) === s` | encoding at most twice as long; encoding uses only input letters (both only test `encode`) |
| `overlaps` | `<` where inclusive end dates need `<=` | a range overlaps itself; agrees with a day-by-day check | symmetry; ranges with a gap never overlap |
| `splitAmount` | every share is `Math.round(cents / n)`, so the remainder is lost or invented | shares sum to the bill | there are n shares; shares differ by at most a cent |
| `firstIndexOf` | ordinary binary search returns *a* copy, not the first | agrees with `indexOf` | any returned index holds the target; −1 only when absent |
| `quote` / `formatRow` | wraps fields in quotes but does not double inner quote marks | `parseRow(formatRow(row))` gives the row back | round trip only for rows without quote marks (a precondition); output at least as long as the fields |

The CSV parser is a strict RFC 4180 single-record parser and is not under test. The date example tests are shown in a readable shorthand (`Mar 1–10`); the code they run uses ISO date strings.

**What is simplified.** The bugs are planted and the functions are tiny; real code has bugs that are harder to state a property for. The shrinker has three passes, where Hypothesis has many more (for example, passes that lower two values together or reorder elements), so its results are locally minimal rather than globally smallest: for `dedupe`, 218 of 300 seeds shrink to `[0, 1, 0]`, and the rest to equally short inputs like `[-1, 0, -1]` or `[2, 0, 2]`. The local-minimality claim is about the choice sequence and the shrinker’s stated neighbourhood, not about every possible smaller input; for `dedupe` the tests also check it on the shown list (no single deletion, and no single value moved towards 0, still fails). Before the sign was drawn for 0 as well, a few `dedupe` seeds ended at `[1, -1, 1]`, where `[1, 0, 1]` still fails; that was a real gap and is why the change was made. Shrink steps are labelled on the page by what changed in the shown input (shorter: “cut a piece out”; otherwise “made a value smaller”, “made it simpler”, or “simplified a hidden choice” when the shown input did not change), not by the internal pass, because deleting choices does not always remove anything visible. There is no example database, no targeted or coverage-guided search, and no stateful testing. The overlap bug always shrinks in a single step, because deleting all four choices gives the all-zero sequence (two one-day ranges on Jan 1), which already fails; when a shrink takes one step or none, the page says why: either the result is the simplest input the generator can make (it then suggests another function), or the first failure was already nearly minimal (it then suggests a new seed). The page starts from a random seed, shown with every run, and each new try uses the next one; no seed on the main page is hand-picked. If a property survives, the scoreboard counts only inputs that were actually tested and reports the ones a precondition skipped separately.

**What I checked, and how.** `node projects/whittle/tests/model.test.js` (about 35 seconds, 61 checks, all seeded). On the last run:

- (a) Every strong property refuted the buggy version within the 1,000-run budget in 1000 of 1000 seeds. Mean inputs needed: dedupe 8.4 (worst 23), run-length 16.9 (worst 48), overlap self 3.4 (worst 58), overlap reference 39.0 (worst 491), split 4.7 (worst 14), binary search 10.4 (worst 35), CSV 4.5 (worst 14). Every weak property survived all 200 seeds × 1,000 runs on the buggy version, as documented; the CSV precondition skipped on average 792 of 1,000 inputs, and the overlap gap property 195.
- (b) For each strong property and 80 seeds: shrinking twice gives identical step sequences; every step still fails and is strictly shortlex-smaller than the one before; the shrinker finished inside its budget; and no neighbour of the result (any delete or zero of a block of 8, 4, 3, 2 or 1 choices, or setting one choice to 0, half, or one less) gives a simpler sequence that still fails. That neighbourhood is rebuilt in the test independently of the shrinker. Known smallest results are pinned: `$0.01 ÷ 2` for the bill, `['"']` for CSV, `'aaaaaaaaaa'` for run-length. Over 300 seeds, shrinks of one step or none: dedupe 19, binary search 7, split 19, run-length 69, CSV 114 (CSV’s smallest failure is a single quote mark, so small first failures are common); the test caps these rates.
- (c) Every fixed version passed every property for 10 seeds × 1,000 runs each (10,000 runs per property, fewer actually tested where a precondition skips).
- (d) Every example test passes on both the buggy and the fixed version.
- (e) The scoreboard strings equal the engine’s counts, and a surviving property with a precondition reports tested and skipped inputs separately; the preview’s fixed seeds still meet its rule (10–40 inputs, 4–9 shrink steps); there is one recorded input per run and the last is the failure; the stage markup and the page’s one paragraph contain no digits; `app.js` has no string with a typed-in count and does not contain the run budget, which it reads from the model.
- Also: replaying any recorded choice sequence rebuilds the same value, the PRNG is deterministic, and the shown `formatRow` behaves like the real one.

I checked the page in a browser at desktop width and at 375 × 812 (no horizontal scroll; long code lines scroll inside the code box), the card preview at 320 × 200, and the projects grid, with no console errors from this page. The browser pane I tested in did not fire `requestAnimationFrame` for a background tab, so the animations were stepped there with a timer shim; the logic and the rendered states were checked, but the frame rate was not measured. After the second round of fixes I also checked that pausing the card mid-demo leaves that demo’s fully whittled frame and requests no further frames, that the version toggle is 40 px tall at 375 px wide, and that a surviving property with a precondition reports tested and skipped inputs separately on the scoreboard, the badge and the lesson. The preview’s five runs take under 0.1 s in Node, down from about 0.3 s when it searched for seeds at load.

**What would change the conclusion.** If the example tests had been written by someone trying to break the code (an input with repeats in a new order, a run of ten, a one-day range), they would have caught each bug too: the point is the attitude, refuting rather than confirming, and generated inputs are a cheap way to keep it. If a property is weak, no number of runs helps, which the page shows directly. And if the fixed versions had a bug outside what the generators produce (huge numbers, Unicode, line breaks in CSV fields), 10,000 survivals would say nothing about it: surviving is not proof.
